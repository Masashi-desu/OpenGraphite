OpenGraphite 運用ドキュメント

このrunbookは、App、ogkiln CLI、MCPでOpenGraphiteを使用する人を主対象にしています。ひとつのWeb正本からprojectを開き、検査、編集、検証、配布する流れを扱います。repository自体の開発手順はコントリビューター付録に分離しています。

01

OpenGraphiteでprojectを開く

ダウンロードページの手順でOpenGraphiteを導入し、Appを起動して「Open Sample Project」または手元の.ogp projectを開きます。projectを開いてpreviewするだけではWeb sourceを書き換えません。

作業に合う操作面を選ぶ

見た目を確認しながら編集する場合はApp、再現可能な検査や自動化にはogkiln CLI、AI clientから同じ検証済みoperationを使う場合はMCPを選びます。3つの操作面は同じCore契約を共有します。

1

ダウンロードページの手順に沿ってOpenGraphiteを導入し、Appを起動します。

2

操作を確認する場合は「Open Sample Project」、実作業では対象projectの.ogp fileを開きます。

3

検査や書き込みの前に、headerに表示されるProjectとPublicのpathが対象と一致することを確認します。

  • ✓対象の.ogp projectが開き、登録pageがcanvasに表示される。
  • ✓表示中のProjectとPublicのpathが編集対象sourceを指している。
  • ✓open、preview、inspectionだけではannotationやsource差分が増えていない。
02

編集可能な正本をひとつに保つ

OpenGraphiteが編集するのは通常のWeb sourceです。標準HTMLが構造と意味、標準CSSが描画値、.ogpがprojectとcanvas metadataを担います。

HTML

semantic tag、標準attribute、読めるfallback contentを使います。optionalなdata-og-id / data-og-internal-idはstable identityが必要な場所だけに置きます。

CSS

design valueは標準propertyへ保存します。projectで共有するtokenは設定済みcssLibrary内の通常のcustom propertyです。

.ogp

登録、canvas配置、viewport、Guide、annotation、reference、preview mockを保持します。page DOMやdesign valueは複製しません。

Generated output

runtime展開DOM、screenshot、static build outputは派生物です。対応するsource resourceをreview・編集します。

04

document全体置換より、text、attribute、style、insert、move、copy operationを優先します。各commandは対象を再検証し、atomicに書き込みます。

  --page-id "$PAGE" \
  --reference '<target-reference-from-dry-run>' \

07

sourceとrendered resultを両方検証する

write成功だけでは完了ではありません。projectをvalidateし、変更page/nodeをcaptureし、配布が必要ならstatic buildを作ります。repository contributorだけが付録の追加quality gateを実行します。

bash コードをコピー コピーしました コピーできませんでした 
PROJECT='SampleProject/OpenGraphiteSample.ogp'
PAGE='ogref:page:1gibtxulofmr0:kl1xxsgkiuue'
OUTPUT_DIR="$(mktemp -d)"

./Scripts/ogkiln validate "$PROJECT" --json
./Scripts/ogkiln screenshot page "$PROJECT" \
  --page-id "$PAGE" \
  --output "$OUTPUT_DIR/home.png" \
  --full-page
./Scripts/ogkiln build "$PROJECT" --output "$OUTPUT_DIR/dist"
  1. Validationerror diagnosticが0件で、warningをすべてreview・説明できる。
  2. Visual変更したviewport、locale、state、responsive conditionが意図した結果と一致する。
  3. Buildstatic outputに.ogp metadataが混入せず、component/slot semanticsを維持する。
  4. Diff意図したWeb sourceとproject metadataだけが変更され、生成物を編集可能な正本として扱っていない。

09

diagnosticsを運用境界として扱う

blockされたwriteを権限拡大や生成物編集で再試行しません。source conditionを解決し、再検査してから新しい最小operationを実行します。

Code必要な対応
incomplete-css-provenance-write-blocked読取不能/external stylesheet、import、未対応selector、target-level provenance gapを解消してからCSS writeを行う。
unsupported-node-capabilitynodeを再queryし、現在のcapability evidenceが対応するoperationを選ぶ。
disallowed-attribute選択tagとcontent modelに適合するcontract-editableな標準attributeを使う。
css-specificity-override-unsafeauthored writable winnerを編集するかselectorを設計し直し、広すぎるoverrideを強制しない。
read-only-css-winnerownershipを明示的にwritable sourceへ移す。read-only winnerをまたぐremoveを推測させない。

完了条件

source diff、validation結果、rendered evidenceが一致している。

別の人やagentが同じprojectを開き直し、変更が安全な理由を理解し、同じ正本から作業を継続できる状態でoperationは完了です。
